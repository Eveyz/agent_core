## MCP live registration + Streamable HTTP transport + UI URL presets

### Problem: MCP servers configured in UI never connected at runtime
- `Brain::from_config` (`core/src/runtime/brain.rs:77`) built the base tool registry without MCP.
- `Brain::build_tool_registry()` (line 405) created a fresh `ToolRegistry::with_defaults()` each
  run — never cloned from base.
- The Tauri app (`app/src-tauri/src/lib.rs`) had no `McpClientManager`, no `connect_all`, and no
  `register_tool_fn` callback. MCP tools were missing from the system prompt AND from the execution
  tool registry.
- The CLI (`cli/src/main.rs:357-392`) had MCP integration but the `register_tool_fn` callback was
  a broken no-op. It registered into `display_registry` only (static display, not per-run).

### Fix: live MCP registration in the Tauri app
- `app/src-tauri/src/lib.rs`:
  - Added `mcp_manager: Arc<AsyncMutex<McpClientManager>>` to `AppState`.
  - In `setup`: create `McpClientManager::from_config`, spawn async `connect_all()`, register a
    `register_tool_fn` callback that builds `McpTool` instances directly (avoids the double-lock
    that `McpTool::register_all` would cause in a sync callback). The callback uses `try_lock` —
    if the manager is busy connecting, it silently skips (next Run picks up tools).
  - In `save_config`: reconnect MCP with new config and replace the central manager. In-flight
    Runs keep using their old manager copy; new Runs pick up the replacement via the callback.
- Imported `McpClientManager`, `McpTool` from `agent_core`.

### Streamable HTTP MCP transport (new `core/src/mcp/http.rs`)
- Implements `StreamableHttpTransport`: POST to a single endpoint with
  `Accept: application/json, text/event-stream`. Handles both plain JSON and SSE-streamed
  responses. Captures `Mcp-Session-Id` for session stickiness. Supports batched responses.
- `McpTool::` add `Http(...)` variant to internal `Transport` enum.
- `connect_one`: routes transport `"http" | "https" | "streamable" | ...` → `StreamableHttpTransport`.
- Dispatch helpers (`transport_request`/`notify`/`is_alive`/`shutdown`): replaced `todo!()` with
  real calls.

### Fix: try_lock race → parking_lot RwLock for tool defs (afternoon)
- Original `register_tool_fn` callback used `mcp_manager.try_lock()` to read tools. If the
  async `connect_all` spawn held the lock when `build_tool_registry` ran, the callback
  silently returned → no MCP tools for that Run → model says "找不到".
- Fix: decoupled tool definitions into `Arc<parking_lot::RwLock<Vec<McpToolDef>>>`.
  After `connect_all` → `*defs.write() = mgr.all_tools()`. Callback reads via
  `defs.read().iter()` — always succeeds (parking_lot RwLock, no contention).
  `McpTool` instances still get the `Arc<AsyncMutex<McpClientManager>>` for execution.
- Updated `save_config` to also refresh `mcp_tool_defs` after MCP reconnection.
- Verified Parallel Search server responds correctly via curl (initialize → tools/list:
  returns `web_search`, `web_fetch` tools).
