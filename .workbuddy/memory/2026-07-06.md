## Audit: subagent lifecycle & execution (4 axes)

Reviewed permission / tools / retry / error-recovery for the subagent execution path. Verified in source:

- **Permission**: child gets exact `permission_config.clone()` (`tools/subagent.rs:319`) — no least-privilege narrowing; a Yolo parent gives Yolo to all children. No per-subagent sandbox subtree.
- **Tools**: `tool_orchestrator.execute_tools` has NO orchestrator-level timeout (only tool-internal: bash 60s, webfetch 30s) → a tool without its own timeout hangs until cancel. `subagents` batch uses unbounded `JoinSet` (`subagent.rs:315`) → N fully-concurrent children can starve the shared tokio runtime.
- **Retry**: tools are never auto-retried (model self-correction only). Subagent bounded by `max_iterations` only, NO wall-clock deadline (`subagent/mod.rs:317` MAX_STREAM_ATTEMPTS=3 but loop has no timeout). No parent-level subagent respawn.
- **Error recovery**: `RunError = Cancelled | Failed(String)` only; recoverability decided by substring keyword match in `RecoveryEngine` (brittle). One malformed tool result → whole run `Err`/abort. No consecutive-error guard beyond iteration cap. Subagent `success:false` surfaced only as text, not structured.

**Already solid**: subagent tool set can't exceed parent + subagent/subagents removed for children (depth≤1); sandbox path hard-deny even in Yolo; HTTP circuit breaker + 429×10 + 5xx×3 + fallback_client; transitive cancel via cloned token + JoinSet drop; Reflector forbids permission escalation.

**Proposed priority order (not yet implemented)**: (1) orchestrator timeout + subagents concurrency cap; (2) subagent execution deadline; (3) typed RecoveryHint + parse-error sanitization + consecutive-error guard; (4) least-privilege permission derivation for subagents. Awaiting user pick to implement one at a time.

## Fixed: per-prompt model not shown (all msgs showed current selected model)

**Symptom**: Switching the model in the input box made every previous message's
model badge update to the new model.

**Root cause**: `App.tsx:95` read the *global* selected model
(`state.settings.config.default_model`) and passed it as `defaultModel` → `ChatArea`
→ `LazyEntry` → `EntryRow` → `UserRow` (`{modelName || '—'}`). No per-message model
existed. DB only stored a single `model_used` per *session* in the `sessions` table;
`session_messages` had NO model column, so resumes lost per-prompt model too.

**Fix — persist + display per-prompt model end-to-end** (frontend clean tsc; core `cargo check` pending):
- `features/chat/types.ts`: `ChatEntry.model?: string`
- `features/chat/chatSlice.ts`: `userMessageSent` payload `{text, model}`; store on user entry; restore `model` from backend `msg.model` on resume; retry preserves `entry.model`
- `features/project/projectSlice.ts`: `FrontendMessage.model?: string`
- `features/chat/utils.ts`: `entriesToMessages` writes `model` for user + assistant
- `components/chat/UserRow.tsx`: display `entry.model || modelName || '—'`
- `App.tsx`: `userMessageSent({ text: msg, model: defaultModel })` (send + retry uses `entry.model ?? defaultModel`)
- `core/src/types.rs`: `Message.model: Option<String>`
- `core/src/memory/storage.rs`: migration `ALTER TABLE session_messages ADD COLUMN model TEXT DEFAULT ''`
- `core/src/session.rs`: INSERT includes `model`; resume SELECT reads `model`
- `app/src-tauri/src/lib.rs`: `FrontendMessage.model`; `to_agent_message` sets it; `resume_session` returns it

## DB Schema 设计审查（记忆 / FTS / 会话 / 工作流）

- 单 SQLite(WAL) 文件，建表集中在 `core/src/memory/storage.rs` init_tables()。共 18 张普通表 + 3 张 FTS5 虚拟表。
- `conversation_summaries` 为死表：仅 CREATE，全代码无读写。
- 检索实际叠了三套：FTS5(持久, 触发器同步) + tantivy BM25(内存, 每次启动从 SQLite 全量重建) + HNSW(内存, `instant-distance` 不可变)。默认配置 BM25+HNSW 都开，主路径走 hybrid(RRF)，FTS5 退化为 fallback/向量候选预筛；archival/agent_memory 的关键词检索仍依赖 FTS5。
- 最大功能隐患：HNSW 不可变，运行期新写入的记忆只进 `fallback` 暴力列表，长会话中新建记忆无法被语义召回，需重启才进图。
- FTS 用隐式 `rowid` 关联 `id TEXT PRIMARY KEY` 表（可用但脆弱：一旦改 INTEGER PRIMARY KEY/WITHOUT ROWID 同步即断）。
- 外键级联已对 sessions/messages/events、cronjobs/runs、workflows 全套齐，设计基本合理。
