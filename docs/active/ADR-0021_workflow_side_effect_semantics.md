## Context

An activity can read data, modify a workspace, or call an external system.
After a crash, the runtime may know that an attempt started without knowing
whether its side effect completed. Blind retry can duplicate changes. Multiple
agents can also race on the same workspace, while upstream handoffs can contain
prompt-injection text.

## Decision

- Every node declares an `EffectPolicy`: `Pure`, `ReadOnly`,
  `WorkspaceWrite`, or `External`.
- Automatic retry is limited to `Pure` and `ReadOnly` attempts and respects a
  persisted attempt limit and absolute backoff deadline.
- Interrupted `WorkspaceWrite` and `External` attempts enter
  `NeedsAttention`; the runtime does not claim exactly-once side effects.
- Each logical node gets a stable `effect_key` across attempts.
- Resource claims are distinct from DAG edges. Workspace-writing custom agents
  conservatively claim the workspace exclusively.
- Effective permissions are the intersection of caller ceiling, workflow
  request, agent declaration, and activity request. Legacy `trusted` workflows
  cannot elevate callers to Yolo.
- Workflow activities cannot wait on an invisible interactive approval.
  Existing whitelist/auto-allow rules still apply; otherwise the unattended
  resolver denies the operation.
- Agent handoffs use `agent.handoff@1`. Explicitly bound upstream values are
  labeled untrusted and never inserted into system instructions.
- Parent cancellation is persisted, propagated to active activities and child
  processes, and does not erase committed history.

## Consequences

### Positive

- Crash recovery does not silently duplicate likely writes.
- Concurrent writers do not overlap in the current single-process worker.
- A child agent cannot expand the caller's authority through its saved config
  or through upstream text.

### Negative / Trade-offs

- Some interrupted runs require a human decision.
- Conservative workspace locking reduces write parallelism.
- Fully interactive durable approvals and cross-process leases/fencing remain
  follow-up work before distributed workers are enabled.

## Alternatives Considered

| Alternative | Pros | Cons | Decision |
|-------------|------|------|----------|
| Retry every failed/interrupted attempt | High automation | Can duplicate destructive or external effects | Rejected |
| Treat every activity as non-retryable | Simple safety rule | Needlessly penalizes pure/read-only work | Rejected |
| Effect-aware retry and conservative write recovery | Useful automation with explicit uncertainty | Requires activity classification | Accepted |
