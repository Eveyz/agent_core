## Context

The previous workflow executor kept dependency state in memory and waited on
topological stages. A process exit could lose completed work or cause the next
launch to mark every run interrupted. Workflow definitions and custom agents
also remained mutable while a run was executing.

## Decision

Use append-only workflow history as the recovery authority:

- `start` freezes the normalized program and adapter versions in a
  `RunManifest`, persists `RunCreated`, then returns a stable Run ID.
- `(request_id)` is unique and makes repeated starts idempotent.
- `(run_id, sequence)` is the ordered history key. Appends use an expected
  sequence and retry optimistic conflicts.
- Scheduling persists `NodeScheduled` and `AttemptStarted` before invoking an
  activity.
- A pure reducer reconstructs the run and node snapshot from the frozen
  manifest plus history.
- The scheduler uses an event-driven ready frontier; a dependent can start as
  soon as its own dependencies complete.
- Published revisions are immutable. Inline programs are also persisted in the
  run manifest.
- On startup, recoverable runs are replayed. Completed nodes are never invoked
  again; interrupted activities follow their effect policy.
- Signals, retry deadlines, and timer deadlines are durable facts. UI clients
  observe snapshots plus history after a sequence cursor.

The initial SQLite migration is additive and keeps legacy workflow tables and
readers intact.

## Consequences

### Positive

- App restart does not discard successful nodes.
- Observation can repair missed UI broadcasts.
- Definitions and agents can be edited without changing an active run.
- The reducer is deterministic and testable without models or wall-clock reads.

### Negative / Trade-offs

- History grows monotonically and needs a future retention policy.
- Projections are currently rebuilt by replay; larger histories may require
  durable snapshots.
- The V1 desktop worker is in-process, so the app must be open to make active
  progress.

## Alternatives Considered

| Alternative | Pros | Cons | Decision |
|-------------|------|------|----------|
| Persist only mutable node status | Simple queries | Loses causality and makes recovery ambiguity hard to audit | Rejected |
| Re-run the workflow from the latest definition | Little storage | Repeats completed work and changes behavior after edits | Rejected |
| Frozen manifest plus append-only history | Deterministic recovery and audit | More storage and reducer code | Accepted |
